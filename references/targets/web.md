# Websites and web applications

## Establish the actual surface

Record origin, product/version clues, selected account/role, plan, locale, and
viewport where they affect behavior. Separate a marketing site, a signed-in
application, documentation, and APIs even when they share branding. Begin with
the user's supplied page or existing tab; preserve a human-controlled session.

Fetch readable pages for content research. Use rendered browser inspection for
client-rendered content and interactions. Map navigation, routes, major screens,
settings, help, integrations, pricing, changelog and relevant documentation.
For a feature catalog, include role/plan-specific areas as inspected or unknown.
For a narrow stack question, focus on implementation evidence instead of crawling
every blog post. Keep a URL/role/state coverage ledger for broad assignments.

## Follow workflows, then explain them

Choose representative inputs and trace entry -> user action -> state change ->
request/local operation -> output. Capture significant screens and interaction
states: empty, loading, successful, invalid, failed, permission-limited and
offline where applicable. Observe persistence and revisit behavior. Use a
test workspace and synthetic inputs for authorized state-changing interactions;
separate real sends, payments, deletions and publication from harmless inspection.

When available, inspect DOM/accessibility structure, delivered scripts and source
maps, response headers, network requests, local storage schemas and service-worker
behavior. Follow only the layers needed for the selected outcome. Use request
paths, payload schemas, timings and responses as evidence while excluding tokens,
cookies, sensitive records and unrelated traffic. A saved HAR is historical:
analyzing it does not authorize replaying its requests or contacting its hosts.

## Interpret fingerprints narrowly

Tag a framework/runtime as observed only when the delivered code or exposed
metadata supports it. Keep backend languages, databases, cloud topology and
models unknown unless sources or behavior establish them. A CDN header locates
a delivery layer; it does not reveal the origin stack. An endpoint or bundle
string may be unused. A job posting describes hiring needs, not necessarily this
feature's deployed implementation. Distinguish the target's stack from a sensible
stack for our replacement.

For market/moat questions, triangulate current docs, integration partners,
customer accounts, interviews and independent reviews. Note dates, incentives,
and claim provenance. Pricing units suggest hypotheses about costs; they do not
prove the implementation or margins.

## Goal-specific handoff

- Understanding: a supported client/server boundary and a trace of the requested
  mechanism, including invisible layers.
- Catalog: routes, roles, controls, states, workflows, data contracts and gaps;
  visual inventory alone is insufficient to establish behavior.
- Recreation: behavioral and visual fidelity requirements separately, representative
  viewport/state captures when visual matching matters, service/data dependencies,
  and independent parity cases. Use original branding/assets or assets the user
  may reuse. Use an available frontend/design skill for the actual UI work.
- Improvement: concrete friction, errors or measured performance linked to the
  relevant flow; distinguish observations from proposed changes.

If authentication, plan access, robots/network restrictions or browser tooling
limits inspection, use accessible docs, supplied captures and public behavior.
Identify exactly which workflows remain unobserved. Do not replace the requested
application with its marketing page and call the application documented.

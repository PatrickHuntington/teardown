# Unfamiliar and mixed targets

Use this route when the target does not fit one conventional software category,
or when the requested result spans several kinds of material. "Anything" means
adapting the investigation, not claiming access or tools the environment lacks.

## Establish an observable contract

1. Identify the actual object and supplied evidence: interactive system, physical
   product, process, recording, design, data, package, or combination. Establish
   version, provenance and access before choosing an instrument.
2. Express the user's question in terms of what can be observed: structure,
   inputs, transformations, state, outputs, constraints, decisions or outcomes.
3. Choose the closest inspection guide for each layer. For example, a hardware
   product may have public manuals (documents), companion software (mobile),
   authorized firmware (artifacts), and a protocol (code and interfaces).
4. Discover suitable available readers/analysis tools and inspect a small
   representative part. Revise the classification based on the result.
5. Build the same evidence and coverage ledger. State unobservable layers and
   identify the specific material/measurement needed to inspect them.

For a physical mechanism or offline business workflow, use supplied measurements,
diagrams, recordings and procedures. Mechanical/material or human behavior cannot
be established by pretending it is a codebase. Keep proposed experiments separate
from measurements actually taken, and follow appropriate domain tooling when
available. Do not invent laboratory/device access.

## Connect layers explicitly

Record how artifacts relate: documentation describes a feature, a screenshot
shows one state, a package contains a client, an API handles a remote operation,
and a publication describes a possible algorithm. These relationships need
evidence; a shared product name alone does not establish matching versions or
implementation. Mark cross-layer hypotheses and test them when consequential.

Choose the outcome playbook by what the user wants to accomplish. Examples:

- A research paper plus sample spreadsheet -> explain and reproduce a method.
- A desktop app plus its web service -> catalog local versus hosted capabilities,
  then assess an offline replacement.
- An interface recording plus API docs -> behavioral spec with explicit unseen
  states, then an independently implemented interaction flow.
- A process manual plus screen captures -> map handoffs and design improvements.

When no supplied evidence can answer part of the request, finish the supported
parts and state the precise gap. Do not silently substitute a different target
or produce a generic SaaS report for an unfamiliar object.
